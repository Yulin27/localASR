为什么先写一层没人看得见的代码

后面几个阶段要接麦克风、辅助功能权限、ASR 模型、本地 LLM。这些 API 会变、会换实现、 会被重写一遍。如果听写的流程本身和它们长在一起，每换一次运行时就要把流程重写一次。

所以先把两件事拆开：流程只描述「我需要什么能力」， 适配器负责「这个能力具体怎么实现」。 DictationCore 里只有前者。

判断这一层做完了没有，标准只有一条：没有麦克风、没有权限、没有网络、没有模型权重， 完整流程也能端到端跑通。现在它可以了 —— 全部 100 个测试都是这么跑的。

形状一次听写经过什么

状态机十个阶段，一个推进者

会话只有一条前进路线。任何进行中的阶段都可以取消或失败，两者都进入终止态； 终止态会停在那里等着，直到用户关掉它，或者再按一次快捷键开始新的会话。

契约十二个端口

端口就是「我需要这个能力」的声明。它们都很窄 —— 没有一个是 Manager 或 Service 那种什么都装的对象， 每个只做一件能被完整描述的事。

后四个是为了让内核不碰全局状态而单独提出来的，原本的架构文档里没有。
端口负责需要注意的地方
AudioCapturing麦克风生命周期多一个 prepare()：先把设备热起来，别让第一个字等开机时间
VoiceActivityDetecting裁掉静音、拒绝空录音返回的是帧区间，不是第二份音频
SpeechRecognizing批量语音识别长音频内部可以分块，但对外只交一个结果
DeterministicTextProcessing不用模型的文字清理永远执行；收得到模式，因为标点和分点方式跟模式有关
TextRefining本地模型书面化交回来的是未经验证的文本
RefinementOutputGuard判断润色结果能不能用不是端口，是核心里一个具体类型 —— 见下
TextInserting把文字送进目标应用永不抛错，投递结果用结构化的值表达
ActiveApplicationProviding抓取前台应用与插入目标永不抛错：没有权限也不该中断录音
ModeResolving决定这次用哪个模式同步纯函数，好在焦点变化之前就定下来
HistoryStoring最近十条记录写失败不影响这次听写
MetricsRecording隐私安全的指标只有计数、耗时、类别，没有文本
DictationSettingsProviding语种、默认模式、润色开关内核不许读 UserDefaults，所以设成端口
TimeSource当前时间同时给墙钟和单调时钟，阶段耗时才能精确断言

为什么输出守卫不是端口。 如果它是端口，任何一个组装处 —— 包括预览用的假程序集 —— 都能塞进去一个更宽松的版本。 那和「让模型自己给自己的输出打分」是同一个漏洞，只是从另一头进来的。

所以它是一个具体的核心类型，只有阈值可以通过 RefinementGuardPolicy 注入， 而且阈值按模式分开：结构化模式本来就该比输入长，消息模式不该。

机制协调器里三个想清楚了的决定

  1. handle() 是同步的

    它只改状态、然后立刻返回；整条流水线跑在自己的 Task 里。 这样「取消」能落在一次正在进行的识别中间，而不是傻等它跑完。

  2. 停止信号用 AsyncStream，没有自己写门

    它天然带闩锁语义（在「准备」阶段就按下的第二次会被缓存，等到地方了立刻生效）、 天然感知取消、而且 yield 是同步的。所以 handle() 一个 await 都不需要。

  3. 推进只有一个入口

    每个阶段切换都走同一个函数。它一次做完三件检查。 这让「迟到的适配器不能污染新会话」变成结构性的保证，而不是每个调用点都要记得写的纪律。

取消要同时用两种手段，因为谁都不能替代谁。
手段能唤醒停在录音等待的会话能中断正在跑的适配器调用
结束停止信号能不能
取消 Task不能 —— 被取消的任务不会自动唤醒停在 continuation 上的等待能
 
// 顺序是有讲究的：先放行停在等待上的，再中断在跑的。
private func cancelActiveSession() {
    guard let session = active else { return }
    stopSignal?.finish()      // 唤醒停在录音等待的会话
    session.task.cancel()     // 中断正在跑的适配器调用
}

失败每一条退路都指向同一个前提

八个端口都可能出问题，处理方式各不相同，但有一条规则贯穿全部： 原始文本一旦产生，就没有任何一条路径能丢掉它。

哪一步出问题协调器怎么做用户说的话还在吗
检测不到语音会话失败，可重试本来就没有内容
静音裁剪报错用未裁剪的整段继续，记录一次降级在
识别失败会话失败，带上类别和阶段没有文本
确定性处理失败把原始文本当作规范化结果，继续走在
润色超时 / 报错最终文本 = 规范化文本，记录原因在
守卫拒绝润色结果同上 —— 空输出、长度越界、语言损坏、混入思考痕迹都会走到这在
插入失败会话仍然算完成，文字留在剪贴板可复制在
写历史失败只报告给指标，这次听写不受影响在

一条容易被忽略的规则：只要文字交给了插入端口，这次会话就会写进历史 —— 哪怕它是被取消的。因为文字可能已经进了用户的文档，而那条历史记录是唯一的凭据。

测试怎么在没有麦克风的机器上测完整流程

十二个端口全部换成假实现，时钟也是注入的 —— 假时钟每被读一次就前进 250 毫秒， 所以阶段耗时是精确的、可以写成断言的值，不需要真的等。

真正让复杂用例可测的是 Latch：它能让某个端口调用停在原地， 测试先去做别的事，再决定什么时候放行。取消和「迟到的结果」这两类最难测的情况， 靠的都是它，而且没有一个 sleep。

过程测试抓出来的五个真问题

这些都不是测试本身的毛病，是实现里的缺陷。列在这里是因为它们说明了这批测试到底在测什么。

插入过程中的取消被悄悄吞掉了

现象在「插入」这一步取消，会话报的是成功。参数化测试里只有这一个边界挂了。

修法插入端口按契约永不抛错，所以它没法报告自己被取消了。在调用之后补一次显式的取消检查。这正是取消测试要按十个边界逐个跑、而不是手写一两个的原因。

状态流把中间阶段丢了

现象订阅者看到的阶段序列是「转写 → 润色」，中间的「规范化」不见了。

修法流的缓冲策略本来设成「只留最新一条」。对渲染够用，但让阶段序列变得不可观测。会话总共只产生十来个小快照，没有理由丢，改成不丢。

准备阶段多读了一次时钟

现象六个阶段的耗时断言里，只有「准备」这一个对不上。

修法上下文里的开始时间另读了一次时钟，而这个时间本来就是按快捷键那一刻。把它改成复用同一个读数，每个阶段边界就正好读一次。

守卫报错了原因

现象混入 <thinking> 的输出被拒绝了，但给的理由是「长度越界」。

修法长度检查排在形状检查前面。而泄漏出来的思考痕迹几乎总是比输入长得多，所以永远先撞上长度这一条。把形状检查提前，才拿得到能用来定位的原因。

取消时没有放开麦克风

现象写假实现时发现的：会话取消了，但没有任何代码去释放采集设备。

修法规则定为「没有产出音频片段就释放设备」。取消发生在录音期间时正好符合；正常停止过的会话则不必多此一举。

偏差和原计划不一样的三处

计划是先定好的，写的时候发现其中三处站不住，改了。

原计划实际为什么
用 RefinementPolicy 这个枚举表达「润色开或关」 拆成 mode 和 isRefinementEnabled 两个字段 确定性处理也要知道模式 —— 标点和分点方式跟模式有关。而「关掉润色」这个分支里塞不下模式，枚举就少了一半信息。
自己写一个 AsyncGate 和一个广播器 两个都不需要 AsyncStream 已经给了闩锁语义、取消感知和同步的 yield；订阅者登记直接放在协调器自己身上，发布就是同步的，顺序不会倒。
只有正常完成的会话才写历史 只要文字交给了插入端口就写 在插入过程中被取消的会话，文字可能已经落到用户文档里了。这时候历史记录是唯一的凭据，不写反而更不安全。
